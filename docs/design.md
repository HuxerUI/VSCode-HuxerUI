# HuxerUI for Visual Studio Code

HuxerUI 0.5.0 is the SDK baseline for the first public extension release. The extension uses the current HuxerUI CLI to create, build, run, watch, deploy, and package projects. A project on a clean machine should go from SDK download to a visible desktop app in VS Code, and a compiler error inside a composable should open the handwritten source.

The first release focuses on CMake desktop development. Android, iOS, and Web use the same CLI workflow on verified host and target combinations. The mcpp preview covers project creation, discovery, desktop builds, and running executable targets.

This design distinguishes **verified behavior**, **extension decisions**, and **prototype requirements**. The source references are pinned to HuxerUI revision `d9c430f`, whose cited files match the inspected checkout. The official 0.5.0 archives are the release acceptance baseline. [HuxerUI source snapshot](https://github.com/HuxerUI/HuxerUI/tree/d9c430fc3b720e09510e041862f98275c2c20f78)

## CLI and execution model

**Verified.** The current CLI uses `--config debug|release` for `build`, `run`, and `package`. Build and run default to Debug, and package defaults to Release. `run` accepts `--watch`. The standalone `--profile` flag enables performance profiling and requires an explicit `--sdk` pointing to a source checkout. Desktop builds invoke CMake. Android uses Gradle and native CMake, iOS uses Xcode, and Web uses Emscripten and CMake. [CLI commands and options](https://github.com/HuxerUI/HuxerUI/blob/d9c430fc3b720e09510e041862f98275c2c20f78/tools/huxerui_cli/cli.cpp#L53-L125) · [Option parsing and SDK selection](https://github.com/HuxerUI/HuxerUI/blob/d9c430fc3b720e09510e041862f98275c2c20f78/tools/huxerui_cli/cli.cpp#L758-L854) · [Platform build dispatch](https://github.com/HuxerUI/HuxerUI/blob/d9c430fc3b720e09510e041862f98275c2c20f78/tools/huxerui_cli/cli.cpp#L1038-L1055)

**Decision.** Open or create a project, resolve its SDK, and bind the absolute path of that SDK's CLI. Each task captures its project root, SDK, executable, target, configuration, and child environment at launch. Use a workspace-folder-scoped VS Code Task Provider for build, run, watch, and package. Commands and shortcuts use the same task definitions. Execute with an argument array and the project root as the working directory. Keep the resolve, spawn, log, and cancellation logic shared across commands. [VS Code Task Provider](https://code.visualstudio.com/api/extension-guides/task-provider)

A typical CMake App uses the following commands, with the extension supplying the bound SDK path and CLI executable.

```shell
huxerui doctor macos
huxerui build macos --config debug --sdk "$SDK_ROOT"
huxerui run macos --config debug --sdk "$SDK_ROOT" --watch
huxerui package macos --config release --sdk "$SDK_ROOT"
```

## SDK installation and selection

**Discover per build host.** List the host's `HUXERUI_HOME`, SDK installations associated with a CLI on `PATH`, official installer locations and their adjacent version directories, and user-registered paths. Validate the installation layout and whether the CLI runs on the host. On an unpinned project, also look for an explicitly configured or nearby HuxerUI checkout. Reuse its CLI from a conventional CMake build directory or build the standalone CLI into the extension cache. [SDK layout and discovery](https://github.com/HuxerUI/HuxerUI/blob/d9c430fc3b720e09510e041862f98275c2c20f78/tools/huxerui_cli/sdk.cpp#L30-L129) · [Standalone CLI build](https://github.com/HuxerUI/HuxerUI/blob/d9c430fc3b720e09510e041862f98275c2c20f78/tools/huxerui_cli/CMakeLists.txt#L1-L7)

**Resolve per project.** A team can commit a folder-level `huxerui.sdkVersion` such as `"0.5.0"`, an exact release constraint. The extension offers to install or select that release when missing. An unpinned project uses its saved local selection, a configured source checkout, a single eligible installed SDK, or a single discovered source CLI. Prompt when a new download or checkout build is needed or several candidates remain. Store SDK and executable paths, source checkout bindings, toolchain paths, and device IDs in user settings or extension state on the execution host. Key local project selections by project root URI so that multiple roots and nested projects can select independently. A project switch applies to subsequent tasks. In mcpp package projects, the manifest and lockfile select the framework dependency. The chosen SDK CLI supplies project scaffolding where applicable. [VS Code settings scopes](https://code.visualstudio.com/api/references/contribution-points#contributes.configuration) · [VS Code multi-root workspaces](https://code.visualstudio.com/docs/editing/workspaces/multi-root-workspaces)

**Install from an official release.** Download the release's `install.sh` on macOS and Linux or `install.ps1` on Windows. The installer selects the archive for the host, verifies the checksum, publishes the installation, and sets the default SDK in the shell profile or Windows user environment. Use the installer's version directory `<prefix>-versions/<version>` so that requests for different releases have distinct destinations. Use the installer's SDK selection mode when the standard installation or the requested version already exists. Project-level selection can bind an already installed version independently of the host default. [Official SDK installation guide](https://github.com/HuxerUI/HuxerUI/blob/main/docs/guide/installation.md)

**Activate for extension tasks.** Pass the selected SDK's `HUXERUI_HOME` and `PATH` to task processes and pass `--sdk` to platform commands that accept it. HuxerUI commands can use the installation immediately. Other tools pick up the installer's environment in new sessions. [CLI process environment](https://github.com/HuxerUI/HuxerUI/blob/d9c430fc3b720e09510e041862f98275c2c20f78/tools/huxerui_cli/cli.cpp#L846-L854)

## Creating and opening projects

**Use a sidebar form.** Show HuxerUI in the Activity Bar when the window has no folders or an open workspace folder is a HuxerUI project. The creation form provides App or Library, name, parent folder, and SDK. Require a lowercase reverse-domain project ID for CMake apps and libraries. Show target platforms directly in the CMake App form and preselect all targets except Web. Show a separate, optional platform integration selector for CMake libraries with no platforms preselected. Keep the build system and mcpp App template under Project Options. `HuxerUI: Create Project` provides the Quick Pick flow in the Command Palette. Both entries invoke the same CLI scaffolding. [VS Code Quick Pick guidance](https://code.visualstudio.com/api/ux-guidelines/quick-picks) · [VS Code Webview guide](https://code.visualstudio.com/api/extension-guides/webview)

| Choice | Creation behavior |
| --- | --- |
| CMake App | Use the built-in App template. Preselect Windows, macOS, Linux, Android, and iOS. Let users enable Web or deselect targets. The platform choice controls generated shells. Show host build availability separately. |
| CMake Library | Default to a common library with a generated `examples/preview` application. Offer optional integrations for Windows, macOS, Linux, Android, iOS, and Web. The CLI generates Preview shells for the selected platforms, or all Preview shells when no integration is selected. When Web is selected, the extension adds the library’s `platform/web/src` directory if the SDK has not created it. Label actions on the generated sample as Preview actions. |
| mcpp App | Offer the built-in App and Navigation templates. Show the Windows, macOS, and Linux scope. The project manifest and mcpp toolchain own target selection. |
| mcpp Library | Use the built-in Library template. Present Build and Test where available. Show Run for an executable target. |
| Advanced fields | Use CLI-derived names and defaults. For CMake libraries, offer a public CMake target and C++ namespace. Offer agent skill files as an opt-in. |

**Delegate scaffolding.** Run `huxerui create app|library <name>` from the selected parent directory. CMake uses the built-in CMake templates. The `--template` selector is for mcpp, whose template uses C++23 modules. Pass the selected CMake App targets or optional CMake Library integration platforms through `--platform`. Omit the flag for a common-only library. Pass `--agent none` when agent files were left unchecked. A released SDK CLI generates a versioned mcpp dependency. The current source checkout flow generates a local path dependency, which the wizard should show before creation. For an existing destination, offer Open Existing or Change Name or Location. The CLI performs the authoritative collision check and stages the new project before publishing it. On success, offer Open Folder or Add to Workspace, followed by an explicit Diagnose and Run action. Select the nearest recognized project to the active file and offer Select Project Root for ambiguous, nested, or custom layouts. Use the selected root as the task working directory. A mixed tree can contain both CMake and mcpp projects. Keep project files under the original project's control and use explicit tasks for custom layouts outside the generated conventions. ## Development workflow

Expose Diagnose Environment, Select SDK, Build, Run, Run with Watch, Stop, Debug, Package, and Open Artifacts in the Command Palette. The sidebar shows the active project, target, and configuration, with an Android or iOS device selector where applicable. Remember the target, configuration, device, optimization, and LTO settings per project. Offer actions based on the selected project and host. Serialize tasks for a project when they share generated files or publication directories. Keep the full command, stage output, working directory, and exit status in the task terminal. [VS Code tasks and problem matchers](https://code.visualstudio.com/docs/debugtest/tasks)

| Entry | Design |
| --- | --- |
| Diagnose Environment | Run `doctor <platform>` for the selected target. Show missing tools with the path or environment setting to fix, and link to platform setup instructions. Launch `setup` only as an explicit interactive task. The current doctor validates an installed SDK and can report a valid source checkout as missing. Verify the checkout and its CLI separately in source mode while preserving platform diagnostics and raw output. Check mcpp and its own toolchain separately. |
| Build and Run | CMake delegates to `huxerui build` and `huxerui run`. For a CMake Library, generated Preview actions use the existing Preview project. In mcpp projects, invoke `mcpp build` and `mcpp run` in the project directory. `huxerui mcpp build` is a forwarding command. The project's `huxerui.rules` and manifest handle framework dependencies, resources, and generated sources. |
| Select Device | Read `huxerui devices android` or `huxerui devices ios`. Show device names, IDs, and readiness. Preselect the last ready device and revalidate it before use. Pass the chosen ID with `--device`. With no ready device, offer the relevant simulator, connectivity, pairing, or authorization instructions. |
| Run with Watch | Use the CLI's watch session. A successful rebuild relaunches the app or refreshes the page, and in-memory application state is rebuilt. A failed build leaves the previous instance running. Surface both states in the task output. |
| Stop | Interrupt managed sessions through their task lifecycle and verify that owned child processes exit. Ordinary macOS launch uses `open`, and mobile deploy commands can return while the app is still running. In those cases, display that the app was launched and expose Stop only for a managed task or watch session. Precise termination of a detached app requires a reliably tracked launch identity. |
| Package and Open Artifacts | Delegate CMake packaging to the CLI, with Release preselected. Open the successful `dist/<platform>` directory or a known artifact from that run. In a remote workspace, reveal the result in the workspace or let the user download it. For the mcpp preview, allow project tasks or its own packaging tooling to own publication. |

[Doctor implementation](https://github.com/HuxerUI/HuxerUI/blob/d9c430fc3b720e09510e041862f98275c2c20f78/tools/huxerui_cli/cli.cpp#L225-L258) · [Platform diagnosis and device output](https://github.com/HuxerUI/HuxerUI/blob/d9c430fc3b720e09510e041862f98275c2c20f78/tools/huxerui_cli/cli.cpp#L616-L725) · [Device selection and Run](https://github.com/HuxerUI/HuxerUI/blob/d9c430fc3b720e09510e041862f98275c2c20f78/tools/huxerui_cli/cli.cpp#L1057-L1153) · [Watch lifecycle](https://github.com/HuxerUI/HuxerUI/blob/d9c430fc3b720e09510e041862f98275c2c20f78/tools/huxerui_cli/watch.cpp#L365-L470) · [macOS launch](https://github.com/HuxerUI/HuxerUI/blob/d9c430fc3b720e09510e041862f98275c2c20f78/tools/huxerui_cli/platform/macos.cpp#L89-L96) · [Package publication](https://github.com/HuxerUI/HuxerUI/blob/d9c430fc3b720e09510e041862f98275c2c20f78/tools/huxerui_cli/cli.cpp#L1232-L1273) · [mcpp forwarding](https://github.com/HuxerUI/HuxerUI/blob/d9c430fc3b720e09510e041862f98275c2c20f78/tools/huxerui_cli/mcpp/mcpp.cpp#L89-L107)

### Host and target matrix

The target picker distinguishes a shell present in the project, a target supported by the SDK and host, and an environment ready to build or run. The host is the machine running the workspace extension. A GUI target also needs a usable display session.

| Target | Host and toolchain | Run and package |
| --- | --- | --- |
| Windows | Windows x64 with CMake, MSVC, Windows SDK, and Ninja or NMake. The CLI selects the CMake generator. | Run the native executable. Package an x64 Burn setup executable. WiX's .NET runtime is a packaging prerequisite. |
| macOS | macOS arm64 or x64 with CMake, Xcode 26 or later, and a compatible SDK archive. The inspected release workflow uses Xcode 26.2. | Run an `.app` and package a `.dmg`. Signing and distribution prerequisites apply per project. |
| Linux | Linux x64 or arm64 with CMake, a compatible C++ toolchain, `pkg-config`, and GTK 4.14 or later with its development dependencies. The inspected official binary baseline is glibc 2.38. | Run in a graphical session. AppImage is the default. DEB and RPM require the project packaging rules and the corresponding native packaging tools. |
| Android | Windows, macOS, or Linux with CMake, JDK, Android SDK, NDK, and Gradle Wrapper dependencies. Use the versions declared by the project and SDK. The source currently specifies NDK `29.0.14206865` and release CI uses JDK 17. | Run on an ADB-accessible emulator or device. Package an APK. The generated template's Release build uses debug signing for development. |
| iOS | macOS with Xcode 26 or later and an installed simulator runtime or paired device. Provision signing for physical devices as required by the project. | Run on the selected destination. Package the built `.app`. Open the Xcode project for native debugging. |
| Web | Windows, macOS, or Linux with the SDK-pinned Emscripten toolchain. The inspected source uses `4.0.19` and runs `emcmake`, `emcc`, and `emrun`. | Run in a browser, and package the HTML, JavaScript, WebAssembly, and resource files for static deployment. |

CMake covers the full platform set and owns Android, iOS, and Web builds. The HuxerUI mcpp path supports Windows, macOS, and Linux with project-selected module toolchains. Its Windows build uses the MSVC ABI, and its Linux workflow can provision GTK dependencies through xlings. The SDK archive supplies framework artifacts and host generators. Toolchains, platform SDKs, and debuggers come from the host or its configured toolchain provider. The desktop extension release matrix uses desktop development hosts. ## Handwritten source, completion, and debugging

### Compiler diagnostics

**Verified.** CMake and mcpp route composable translation units through `hcg`. The generator emits `#line` directives naming the handwritten file, and its own syntax errors include the input path, line, and column. A macOS command-line probe produced a compiler error at the handwritten `src/app.cpp:7:10` while the actual compiler input was a generated `hcg/.../app.cpp`. [CMake code generation](https://github.com/HuxerUI/HuxerUI/blob/d9c430fc3b720e09510e041862f98275c2c20f78/cmake/HuxerUICodegen.cmake#L175-L235) · [mcpp code generation](https://github.com/HuxerUI/HuxerUI/blob/d9c430fc3b720e09510e041862f98275c2c20f78/mcpp/huxerui-build-rules/src/rules.cppm#L190-L218) · [Source line directives](https://github.com/HuxerUI/HuxerUI/blob/d9c430fc3b720e09510e041862f98275c2c20f78/tools/codegen/transform.cpp#L851-L891) · [Generator diagnostics](https://github.com/HuxerUI/HuxerUI/blob/d9c430fc3b720e09510e041862f98275c2c20f78/tools/codegen/main.cpp#L96-L116)

**Decision.** Populate VS Code Problems from Clang, GCC, MSVC, CMake, and `hcg` output. Use the original path reported by the tool and resolve it in the task's host and workspace. Handle spaces, drive letters, path casing where relevant, and tool-specific column conventions. Scope diagnostics to the project and clear resolved entries on the next build or watch cycle. Surface paths in generated files as reported when the tool has no reliable original location. Keep full context in the task terminal for configure, Gradle, or Xcode failures that lack usable source coordinates.

### C++ editor and debugger integration

| Component | Dependency decision |
| --- | --- |
| CMake Tools | Installed by the HuxerUI extension pack for CMake configure, target navigation, and C/C++ configuration. HuxerUI tasks invoke the SDK CLI. |
| Microsoft C/C++ | Installed by the HuxerUI extension pack for completion, navigation, code analysis, and desktop debugging on Windows and Linux. clangd remains an alternative for language features. Use one primary C++ language provider per workspace. |
| Debug adapter | Required only for the selected Debug action. Offer Microsoft C/C++ with `cppvsdbg` on Windows, `cppdbg` with GDB or an approved LLDB configuration on Linux, and CodeLLDB on macOS after validation. Delegate native Android and iOS debugging to Android Studio and Xcode. Web debugging uses browser developer tools. |

[Microsoft CMake Tools presets](https://github.com/microsoft/vscode-cmake-tools/blob/main/docs/cmake-presets.md) · [Microsoft IntelliSense configuration](https://code.visualstudio.com/docs/cpp/configure-intellisense) · [C/C++ debug configuration](https://code.visualstudio.com/docs/cpp/launch-json-reference) · [CodeLLDB manual](https://github.com/vadimcn/codelldb/blob/master/MANUAL.md)

**Completion and navigation.** The macOS CMake sample compiled the generated translation unit, and the CMake Tools provider alone missed SDK completions in the handwritten file. HuxerUI supplies the selected SDK's include path as a C/C++ fallback and excludes generated composable copies from the C/C++ index. The macOS sample verified SDK completion and definition jumps to the SDK header and the handwritten composable. Verify several composables, conditional platform includes, and multi-root configuration switches. Where the fallback is insufficient, prototype an editor-only compile entry for the handwritten file using a verified original-to-generated pair. Preserve the actual include paths, defines, compiler and sysroot. For mcpp, consume the compilation information produced by the installed mcpp version and validate `.cppm` files and BMI flags separately. If a dependable pairing is unavailable, the SDK build rules can export the source pairs they already know. [CMake compile database support](https://cmake.org/cmake/help/latest/variable/CMAKE_EXPORT_COMPILE_COMMANDS.html) · [clangd compile commands](https://clangd.llvm.org/design/compile-commands) · [mcpp compilation database](https://github.com/mcpp-community/mcpp/blob/main/docs/04-mcpp-toml.md)

**Breakpoint prototype.** Build Debug with the selected SDK and use the actual binary and environment for the debug adapter. CMake emits a configuration-specific application integration plan with target, executable, and bundle paths. Read the plan for the selected task and allow a user-provided executable for custom layouts. LLDB bound a breakpoint on the handwritten composable line in the macOS command-line probe. Validate an actual VS Code launch and breakpoint hit, stepping and stack paths, PDBs on Windows, and DWARF on Linux. Use adapter source path mapping for relocated or remote paths. [CMake app integration plan](https://github.com/HuxerUI/HuxerUI/blob/d9c430fc3b720e09510e041862f98275c2c20f78/cmake/HuxerUIApp.cmake#L285-L309) · [VS Code debugger extension guide](https://code.visualstudio.com/api/extension-guides/debugger-extension)

## Trust and remote development

Run as a Node workspace extension with `extensionKind: ["workspace"]`. In Remote SSH, WSL, and Dev Containers, use the remote filesystem, SDK storage, CLI, toolchain, and debug backend. WSL follows Linux host rules. A headless host can build and package and should report the missing display session when a GUI run is requested. Devices need to be reachable from the execution host. Provide an in-workspace path to a remote artifact and an explicit download action for local use.

In Restricted Mode, detect project markers and show the available documentation. Require workspace trust before invoking a project command, probing an executable, installing an SDK, or starting a build, deployment, watch, or debug session. Pure virtual workspaces can expose project information through VS Code's filesystem API. Remote Web preview is a follow-up once there is a reliably reported loopback URL and a validated stop lifecycle. Forward the URL with VS Code port forwarding and `asExternalUri`. [Workspace Trust](https://code.visualstudio.com/api/extension-guides/workspace-trust) · [Extension host placement](https://code.visualstudio.com/api/advanced-topics/extension-host) · [Remote extension guidance](https://code.visualstudio.com/api/advanced-topics/remote-extensions) · [Virtual workspaces](https://code.visualstudio.com/api/extension-guides/virtual-workspaces)

## Release acceptance checklist

- [ ] **Install through first run.** On clean Windows x64, macOS arm64, and Linux x64 hosts, install the official 0.5.0 SDK through the extension. Check the installer's registered `PATH` and `HUXERUI_HOME` in a new session. In the original VS Code window, confirm an actionable diagnosis with a missing build tool, install or configure the tool, create a CMake App, run it, and observe a window.
- [ ] **Side-by-side installation.** Install another release through the extension and verify the original SDK remains usable. Switch project selection between installed SDKs and verify the host default stays as selected by the installer. Try an unavailable release, an incompatible architecture, cancellation, and two windows requesting the same installation.
- [ ] **Independent multi-root projects.** Use two separately installed copies of 0.5.0 in the same workspace. Run one root in Debug and build the other in Release. Verify executable path, SDK root, `--config`, working directory, artifacts, and Problems entries for both. Switch one root and repeat. Also verify a 0.5 source checkout binding with its own CLI.
- [ ] **Open existing projects.** Open an existing CMake App, CMake Library with Preview, and mcpp App. Build or run with their existing project files and compare the source tree before and after. Verify nested root selection and creation conflicts with both empty and non-empty destination directories.
- [ ] **Generated code diagnostics.** Add an undefined symbol inside a handwritten composable, then trigger an `hcg` conversion error separately. Select each Problems entry and verify the handwritten file, line, and column. Repair both and verify diagnostics clear. Include a source path containing spaces and exercise Windows drive paths and one remote path.
- [ ] **Completion and Debug.** Check that completion and go-to-definition work from representative handwritten sources with the selected target's include paths and defines. Launch a Debug build, hit a composable breakpoint, and verify stepping and the stack source path. Check PDB and DWARF separately. Track mcpp modules and BMI support as preview results.
- [ ] **Watch and stop.** Start a watch session, change a source file, and observe the app relaunch. Introduce a build error and verify the previous instance remains usable. Fix it and verify recovery. Stop the task and confirm owned processes are gone. Verify the UI reports app launch and task ownership accurately for detached runs.
- [ ] **Platform and packaging checks.** Validate macOS to an Android emulator, macOS to an iOS simulator, and Linux to a local Web browser. Exercise device selection, zero ready devices, and missing tooling. Package each desktop target on its host and verify that Open Artifacts resolves the successful output. Check the APK, iOS app bundle, and Web asset locations for supported cross-target workflows.
- [ ] **Remote and restricted workspaces.** Build in WSL and a Dev Container and verify the SDK, toolchain, outputs, and diagnostic links are remote. Check that a headless workspace reports GUI availability accurately. Open a project in Restricted Mode, verify that it starts zero external processes, then grant trust and explicitly run a build.
